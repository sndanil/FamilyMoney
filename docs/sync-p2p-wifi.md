# Прямая синхронизация по Wi-Fi: проект

Статус: **core-прототип этапа 1 реализован**; сетевой слой и UI ещё не начаты.
Документ дополняет [sync-alternatives.md](sync-alternatives.md) и опирается
на уже сделанные этапы 0–2.

## 1. Цель

Дать телефону и десктопу возможность обменяться изменениями **напрямую по одному Wi-Fi**,
без облака, интернета и внешнего сервера:

- телефон и компьютер в одной локальной сети;
- оба приложения открыты;
- пользователь открывает на десктопе «Синхронизация по Wi-Fi», сканирует QR телефоном;
- изменения едут в обе стороны;
- облачная синхронизация (S3/WebDAV/папка) остаётся доступной и не ломается.

Не цель первого этапа: фоновая синхронизация, автоматическое обнаружение без QR,
работа через интернет, замена облака, слияние двух разных баз.

## 2. Краткое решение

1. **Десктоп — хост, телефон — клиент.** Телефон всегда инициирует соединение.
   Это снимает главную проблему Android: приложение не может надёжно держать сервер
   в фоне. Десктоп слушает только пока открыт диалог синхронизации.
2. **QR-пейринг на одну сессию.** QR содержит IP, порт, отпечаток TLS-сертификата и
   одноразовый токен. Никаких облачных ключей и ключа E2E в этом QR нет.
3. **TLS + pinning + одноразовый токен.** Самоподписанный сертификат десктопа,
   отпечаток в QR; телефон принимает только этот сертификат.
4. **Не перекладываем журналы этапа 2, а делаем state-based anti-entropy.**
   Каждая сторона отдаёт записи, у которых `LastChange` больше известной отметки
   (watermark), и применяет чужие через уже существующий `ApplySyncDelta`.
   Это не зависит от outbox и от того, настроено ли облако.
5. **Облако и Wi-Fi сосуществуют.** P2P не очищает облачный outbox и не пишет
   облачные журналы; после P2P облачная синхронизация продолжает работать как раньше.
6. **MVP — только «оба открыты, вручную, по QR».** mDNS, доверенные устройства,
   фоновый режим и обмен снапшотами — отдельные этапы.

## 3. Почему не гоняем журналы этапа 2 напрямую

Журналы `devices/{deviceId}/...` — это формат **объектного хранилища**. Чтобы телефон
синхронизировался с десктопом через них, десктоп должен был бы отдавать наружу
свой объектный store. Но:

- десктоп может быть настроен на S3/WebDAV, а не на локальную папку;
- без интернета облачный store недоступен;
- если делать локальное зеркало журналов, появляется второй источник истины и
  отдельная reten-политика;
- телефон должен был бы писать в чужой префикс или ждать, пока десктоп заберёт
  его журнал.

State-based подход использует то, что уже есть в LiteDB: `LastChange` у каждой
сущности и `ApplySyncDelta` с LWW. Ему не нужны ни облако, ни журналы, ни outbox.
Журналы этапа 2 остаются форматом облака; P2P — второй, независимый транспорт.

Компромисс: передаются **целые изменённые сущности**, а не патчи полей; первая
синхронизация отправляет все записи. Для семейной базы это приемлемо, а для
больших баз добавляется пагинация и, позже, снапшот.

### 3.1 Рассмотренные варианты

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| Пир как объектный store с журналами этапа 2 | переиспользует весь облачный протокол | десктопу нужен локальный store/зеркало; без облака не работает | нет |
| State-based anti-entropy по `LastChange` | не зависит от облака и outbox; использует `ApplySyncDelta`; mesh сходится | передаёт целые сущности; первая синхронизация полная | **да** |
| Копирование файла БД | быстро для новой базы | перезаписывает локальные данные; не годится для слияния | позже, только bootstrap |
| Телефон-хост | симметрично | Android не держит сервер в фоне; foreground service | не в MVP |
| mDNS-обнаружение | без QR | multicast, разрешения, нестабильно в гостевых сетях | позже |

## 4. Архитектура

```
┌──────────────────────────┐                 ┌──────────────────────────┐
│ Android                  │                 │ Desktop                  │
│                          │   TLS 1.2/1.3   │                          │
│ PeerSyncClient ──────────┼────────────────►│ PeerSyncServer           │
│   TcpClient              │  framed JSON    │   TcpListener + SslStream│
│   SslStream              │  + image bytes  │   self-signed cert       │
│   Certificate pinning    │                 │   one-time token         │
│                          │                 │                          │
│ PeerSyncEngine           │                 │ PeerSyncEngine           │
│   IRepository            │                 │   IRepository            │
│   PeerSyncStateStore     │                 │   PeerSyncStateStore     │
│   SyncDelta/ApplyDelta   │                 │   SyncDelta/ApplyDelta   │
└──────────────────────────┘                 └──────────────────────────┘
```

Компоненты:

| Компонент | Где | Назначение |
|---|---|---|
| `PeerSyncEngine` | core | оркестрация: hello, pull, push, watermarks, прогресс |
| `PeerSyncServer` | desktop | listener, TLS, приём одного клиента, диспетчеризация |
| `PeerSyncClient` | Android (и тесты) | подключение, TLS pinning, запросы |
| `PeerProtocol` | core | кадры, DTO, лимиты, ошибки |
| `PeerSyncStateStore` | core | watermark’и по peer deviceId |
| `PeerPairingPayload` | core | QR: host/port/fingerprint/token/syncId |
| `PeerHostViewModel` / `PeerSyncWindow` | desktop | QR, статус, прогресс, отмена |
| `PeerSyncViewModel` | Android | сканирование QR, прогресс, ошибки |

`PeerSyncEngine` не знает, откуда пришли байты: в тестах используется in-memory
транспорт, в приложении — TCP/TLS. Это позволяет протестировать слияние без сети.

## 5. Модель синхронизации

### 5.1 Watermark’и

Для каждой пары устройств хранится две отметки:

- `AppliedFromPeer` — максимальный `LastChange`, который **мы применили** из
  данных пира; запрос идёт по `LastChange >= watermark`;
- `PeerAppliedFromUs` — последний подтверждённый пиром watermark наших данных
  (для статуса; источник истины — состояние пира).

Они не равны глобальным часам и не являются ревизиями облака. Это просто границы
для запроса «что изменилось с тех пор». Запрос идёт по `LastChange >= watermark`;
поэтому граница всегда на 1 мс больше последней отданной записи. Записи на самой
границе могут прийти повторно — это безопасно, применение идемпотентно.

Файл состояния:

```
{HomeFolder}/sync/peers/{syncId:N}/{peerDeviceId}.json
```

```json
{
  "DatabaseSyncId": "…",
  "PeerDeviceId": "…",
  "PeerName": "Ноутбук",
  "AppliedFromPeer": "2026-11-14T17:00:00Z",
  "PeerAppliedFromUs": "2026-11-14T16:55:00Z",
  "LastSyncAt": "2026-11-14T17:00:03Z"
}
```

При новой паре обе отметки — `DateTime.MinValue`; это значит «пришли всё».

### 5.2 Сессия

Телефон (клиент) выполняет:

1. `Hello` — `syncId`, `deviceId`, `deviceName`, одноразовый токен.
2. `HelloAck` — сервер отдаёт свой `serverAppliedFromClient` (что он уже принял
   от этого телефона). Это авторитетная граница для push.
3. `Pull` — сервер отдаёт изменения с `LastChange >= appliedFromServer`.
4. Клиент применяет сущности, затем картинки. Если картинка не скачалась —
   сессия не двигает watermark и завершается ошибкой; повтор скачает заново.
5. Клиент сохраняет `appliedFromServer = watermark` (максимальный `LastChange`
   порции); для следующей страницы использует `next`.
6. `Push` — клиент отдаёт изменения с `LastChange >= serverAppliedFromClient`.
7. Сервер применяет сущности и картинки; только после успеха отвечает новым
   `serverAppliedFromClient` (watermark) и `next` для страниц.
8. Клиент сохраняет `serverAppliedFromClient` и `lastSyncAt`.

Сервер в это время:

- проверяет токен, `syncId`, протокол;
- читает свой peer-state (если пира нет — `MinValue`);
- на `Pull` строит `SyncDelta` из `GetSyncChangesSince(since)`;
- на `Push` применяет `ApplySyncDelta` и `ApplySyncedImagesAsync`;
- обновляет peer-state **после** успешного применения;
- отдаёт прогресс в UI.

Состояние сервера считается авторитетным: если оно потеряно, сервер вернёт
`MinValue`, и телефон пришлёт все изменения заново (это идемпотентно). Если
потерян `HelloAck`, телефон повторит push с более старой отметки; дубликаты
безопасны.

### 5.3 Что именно читаем

Новый метод репозитория:

```csharp
public sealed record SyncChangesBatch(
    SyncPendingChanges Changes,
    DateTime Next,       // курсор следующей страницы (max + 1 мс)
    DateTime Watermark,  // max LastChange порции, сохраняется в состоянии
    bool HasMore);

SyncChangesBatch GetSyncChangesSince(DateTime since, int maxRecords = 2000);
```

Он должен вернуть:

- аккаунты, категории, подкатегории и транзакции с `LastChange >= since`,
  **включая удалённые** (tombstones);
- метаданные картинок `_SyncImageMeta`/`_SyncImageOutbox` с `LastChange >= since`;
- `Next` — следующая миллисекунда после максимального `LastChange` среди отданных
  записей (эксклюзивная граница следующей страницы);
- `HasMore`, если записей больше лимита; записи с одинаковым `LastChange`
  не разрезаются между страницами.

Внутри — обычные LiteDB-запросы по коллекциям; не `GetAccounts()`/`GetTransactions()`,
потому что те фильтруют удалённые и ограничивают период. Записи превращаются в
`SyncOutboxEntry`/`SyncImageOutboxEntry` и складываются в `SyncDelta` через
`SyncDeltaBuilder`; ничего нового в формате дельты не появляется.

### 5.4 Применение

Используем существующие:

- `IRepository.ApplySyncDelta(SyncDelta)` — LWW по `LastChange`, пересчёт балансов,
  `SyncContext.EnterApplyScope()` (не попадает в облачный outbox);
- `IRepository.ApplySyncedImagesAsync(...)` — картинки и их tombstone’ы.

Это значит, что P2P-слияние ведёт себя так же, как облачное, и не создаёт
циклов «применил чужое → отправил обратно».

### 5.5 Конфликты

Правило одно и то же для облака и Wi-Fi: **LastChange wins**. Если оба изменили
одну запись, победит более поздняя по времени. Часы устройств должны быть
примерно синхронизированы; это уже допущение текущей модели. Отдельного
журнала конфликтов в MVP нет.

### 5.6 Картинки

- В `Pull` приходят `SyncImageRecord`; клиент по одному запрашивает байты.
- В `Push` клиент отправляет метаданные, затем байты; сервер применяет через
  `ApplySyncedImagesAsync`.
- `DeletedAt` — удаление; байты не передаются.
- Если байты не передались, watermark не двигается; повтор идемпотентен.
- Формат кадра для картинки: заголовок с длиной + сырые байты, без base64.

### 5.7 Новое устройство

Если телефон пустой:

- в QR есть `syncId`; приложение предлагает «подключиться к этой базе»;
- при согласии телефон получает `syncId` и тянет все записи (`MinValue`);
- отдельный снапшот БД не нужен: state-based pull сам отдаст всё.

Если на телефоне уже есть данные:

- при совпадении `syncId` — обычное слияние;
- при другом `syncId` — отказ, чтобы не смешать две семьи/две базы;
- снапшот поверх локальной базы не восстанавливается.

### 5.8 Сосуществование с облаком

- P2P **не очищает** `_SyncOutbox` и не пишет `devices/...`.
- Локальные изменения остаются в outbox и уедут в облако при следующей облачной
  синхронизации.
- Чужие изменения, применённые по Wi-Fi, идут через apply scope и в outbox не попадают.
- Облачная и P2P-синхронизация не должны идти одновременно: нужен общий
  `SyncOperationGate` (семафор), которым пользуются `SyncService` и `PeerSyncEngine`.
  Иначе две операции могут одновременно применять дельты и пересчитывать базы.

## 6. Протокол

### 6.1 Транспорт

- TCP, `TcpListener` на выбранном IPv4-адресе, порт `0` (ОС выдаёт свободный).
- TLS 1.2/1.3 через `SslStream`.
- Самоподписанный сертификат генерируется на сессию (RSA 2048, SHA-256,
  срок 1 день).
- Клиент проверяет **точный** SHA-256 отпечаток сертификата из QR, а не цепочку.
- Никакого HTTP: свой простой framed-протокол. Это избегает URL ACL,
  администраторских прав и ASP.NET Core runtime на десктопе.

### 6.2 Кадры

```
[4 байта big-endian длина][UTF-8 JSON]
```

- Максимальный JSON-кадр — 16 МиБ; при превышении — разбиение на страницы.
- Картинки — отдельные кадры: заголовок JSON + сырые байты длиной до 64 КиБ
  (или один кадр на картинку с длиной; лимит 8 МиБ).
- Таймауты: handshake 10 с, простой 60 с, сессия 10 мин (настраивается).

### 6.3 Сообщения

`Hello` (клиент → сервер):

```json
{
  "type": "hello",
  "protocol": 1,
  "syncId": "…",
  "deviceId": "…",
  "deviceName": "Телефон",
  "token": "base64url"
}
```

`HelloAck` (сервер → клиент):

```json
{
  "type": "hello",
  "protocol": 1,
  "syncId": "…",
  "deviceId": "…",
  "deviceName": "Ноутбук",
  "serverAppliedFromClient": "2026-11-14T16:55:00Z",
  "serverNow": "2026-11-14T17:00:01Z"
}
```

`Pull`:

```json
{ "type": "pull", "since": "2026-11-14T17:00:00Z", "maxRecords": 2000 }
```

`Changes`:

```json
{
  "type": "changes",
  "delta": { "accounts": [], "categories": [], "subCategories": [], "transactions": [], "images": [] },
  "next": "2026-11-14T17:00:06Z",
  "watermark": "2026-11-14T17:00:05Z",
  "hasMore": false
}
```

`next` — курсор следующей страницы (на 1 мс позже `watermark`), `watermark` —
максимальный `LastChange` в порции; в состоянии пары сохраняется именно он.

`Push` — тот же `delta`; `PushAck`:

```json
{
  "type": "pushAck",
  "serverAppliedFromClient": "2026-11-14T17:00:06Z",
  "next": "2026-11-14T17:00:07Z"
}
```

Картинки:

```json
{ "type": "imageRequest", "entityId": "…" }
{ "type": "image", "found": true, "fileName": "receipt.jpg", "length": 12345 }
```

Дальше `length` сырых байт. Для отправки — `imageUpload` с такими же полями и байтами.

Ошибки:

```json
{ "type": "error", "code": "badToken|badSyncId|protocol|busy|internal", "message": "…" }
```

### 6.4 Пагинация

`GetSyncChangesSince` ограничивает batch (например, 2000 записей). Клиент
повторяет `Pull`, пока `hasMore == true`, и после каждого успешного batch
сохраняет `watermark` (максимальный `LastChange`), а для следующей страницы
берёт `next` — на 1 мс позже. Если в batch есть картинки, они скачиваются до
перехода к следующему batch. Записи с одинаковым `LastChange` не разрезаются
между страницами.

### 6.5 Идемпотентность

Повторный `Pull`/`Push` безопасен: `ApplySyncDelta` и `ApplySyncedImagesAsync`
сами решают по `LastChange`, применять ли запись. Повтор после обрыва
начинается с последнего сохранённого watermark.

## 7. Безопасность

### 7.1 Что защищаем

- данные семейной базы в локальной сети;
- доступ к синхронизации с чужого устройства в той же Wi-Fi;
- подмену сервера (MITM) в локальной сети.

### 7.2 Меры

- TLS 1.2/1.3, самоподписанный сертификат.
- Отпечаток сертификата в QR; клиент принимает только его.
- Одноразовый токен в QR, TTL 10 минут, одна успешная сессия.
- Сервер принимает **одно** подключение и только пока открыт диалог.
- Проверка `syncId` и версии протокола.
- Bind только на выбранный локальный IPv4, не `0.0.0.0` без необходимости.
- Никаких секретов облака/ключа E2E в QR.
- В логах нет токена и содержимого дельт.

### 7.3 Что не делаем в MVP

- постоянные доверенные устройства (каждый раз QR);
- mDNS-обнаружение;
- E2E-шифрование payload поверх TLS. TLS здесь и есть end-to-end между
  двумя приложениями; третьей стороны нет. Если понадобится паритет с
  облачным E2E, можно позже обернуть JSON через `SyncCrypto`.
- защита от пользователя, который сам сфотографировал QR и передал токен.

### 7.4 Android 17+

Начиная с Android 17 (API 37) доступ к локальной сети требует runtime-разрешения
`ACCESS_LOCAL_NETWORK` для приложений, ориентированных на 37+. Это касается и
исходящих TCP-подключений на локальные адреса. Нужно:

- добавить `<uses-permission android:name="android.permission.ACCESS_LOCAL_NETWORK" />`;
- запрашивать разрешение перед подключением (аналогично RECORD_AUDIO в `MainActivity`);
- на API < 37 не показывать запрос;
- проверить target SDK при обновлении .NET Android.

Ссылка: [Local network permission — Android Developers](https://developer.android.com/privacy-and-security/local-network-permission).

## 8. Платформы и сеть

### 8.1 Десктоп

- `TcpListener` + `SslStream`; без ASP.NET Core/Kestrel и без URL ACL.
- Список IPv4-адресов: Wi-Fi в приоритете, затем Ethernet; пользователь выбирает,
  если адресов несколько.
- Порт — эфемерный; QR содержит фактический.
- Windows Firewall: первый запуск может показать запрос; разрешить только
  частные сети. Если соединение не устанавливается — подсказка про firewall.
- Хост живёт, пока открыт диалог; закрытие/отмена останавливает listener.
- VPN/виртуальные адаптеры могут дать неверный адрес; показываем выбор.

### 8.2 Android

- Клиент `TcpClient` + `SslStream`, таймаут подключения 8 с.
- `INTERNET` уже есть; добавить `ACCESS_LOCAL_NETWORK` (см. выше).
- QR-сканер уже есть (`IQrScannerService`), используем его.
- Приложение должно быть на переднем плане; экран можно удерживать включённым
  на время сессии.
- Гостевая Wi-Fi/AP isolation: соединение не устанавливается; сообщение
  «проверьте, что устройства в одной сети и сеть не изолирует клиентов».
- Мобильный интернет не используется; если Wi-Fi нет — кнопка недоступна.

### 8.3 Обнаружение

MVP — **только QR**. mDNS/UDP broadcast не нужен:

- меньше разрешений и кода;
- не зависит от multicast;
- IP меняется — просто новый QR.

mDNS можно добавить позже для «повторно подключиться к знакомому ноутбуку»,
но это отдельный этап.

## 9. UX

### 9.1 Десктоп

Кнопка «Синхронизировать по Wi-Fi» в настройках синхронизации/на главной.
Она не требует настроенного облака: P2P работает с локальной базой и доступна
для активной базы даже при выключенном S3/WebDAV.

Диалог:

```
Синхронизация по Wi-Fi
[QR-код]
Ноутбук · 192.168.1.42:51234
Отпечаток: A1:B2:… (короткий)
Ожидание телефона…
[Отмена]
```

После подключения:

```
Подключён: Телефон
Получено: 12 записей, 2 фото
Отправлено: 3 записи
Готово
```

Ошибки: нет Wi-Fi, firewall, телефон не сканирует, не та база, истёк QR.

### 9.2 Телефон

Настройки → «Синхронизация по Wi-Fi» → сканировать QR → прогресс → готово.

Если база пустая и `syncId` отличается — предложить «Подключиться к базе
„Семейный бюджет“?». Если база непустая — отказ с объяснением.

### 9.3 Общее

- Обе стороны показывают прогресс и позволяют отменить.
- После успеха — сообщение и обновление экранов (`DatabaseChangedMessage`).
- Если пользователь изменил данные во время сессии, следующие изменения
  уедут в следующей сессии (watermark).
- Никаких автоматических повторных подключений в MVP.

## 12. Тесты

### Core

- пустой телефон + заполненный десктоп: полный pull;
- оба пустые: успех без изменений;
- изменения только на телефоне: push;
- изменения только на десктопе: pull;
- оба изменили разные записи: обе применяются;
- оба изменили одну запись: LWW;
- удаление и tombstone;
- картинка: upload/download/delete;
- повторный pull/push идемпотентны;
- watermark не двигается при ошибке картинки;
- `syncId` mismatch;
- P2P не меняет облачный outbox.

### Сеть

- loopback TLS handshake;
- неверный отпечаток — отказ;
- неверный токен — отказ;
- неверный `syncId` — отказ;
- таймауты и отмена;
- большой кадр/пагинация;
- обрыв после pull до push — повтор.

### Ручные

- Windows Firewall: разрешено/заблокировано;
- guest Wi-Fi/AP isolation;
- Android 17 permission deny/allow;
- смена IP — новый QR;
- экран погас/приложение свернули — сессия отменяется;
- два телефона по очереди к одному десктопу.

## 13. Риски и ограничения

| Риск | Смягчение |
|---|---|
| Android не держит сервер в фоне | десктоп-хост, телефон-клиент |
| Оба приложения должны быть открыты | явный ручной режим, статус |
| AP isolation/гостевая сеть | сообщение, проверка same subnet |
| Windows Firewall | инструкция, разрешение частных сетей |
| IP меняется | QR на каждую сессию |
| Большая первая синхронизация | пагинация, прогресс; позже снапшот |
| Сбитые часы | LWW как в облаке; предупреждение |
| P2P и облако одновременно | общий `SyncOperationGate` |
| Утечка QR | одноразовый токен, TTL, TLS pinning |
| Android 17 local network permission | манифест + runtime-запрос |
| Потеря изображения | watermark не двигается, повтор |
| Старый клиент | protocol version, отказ |

## 14. Открытые вопросы

1. **Телефон как хост.** Нужен ли сценарий «десктоп подключается к телефону»?
   Для MVP предлагаю нет: это требует foreground service и сильно усложняет Android.
2. **Постоянные доверенные устройства.** MVP — QR на каждую сессию. Позже можно
   хранить peer-ключ и подключаться без QR.
3. **E2E payload поверх TLS.** Предлагаю не делать: TLS уже между приложениями.
   Если нужен паритет с облачным E2E — отдельный этап.
4. **Снапшот для первого подключения.** State-based pull проще и не перезаписывает
   локальную базу. Если первая синхронизация окажется медленной — добавить
   снапшот как оптимизацию.
5. **mDNS.** Не нужен для MVP; QR надёжнее.
6. **Несколько баз.** Синхронизируем только выбранную активную базу, как облако.

## 15. Что уже сделано

Этап 1 реализован в core, без сети и UI:

- `SyncChangesBatch` и `IRepository.GetSyncChangesSince`;
- запрос по `LastChange`, включая tombstone'ы и картинки, с пагинацией;
- `PeerSyncState`/`PeerSyncStateStore`;
- `PeerSyncClientEngine` и `PeerSyncServerEngine`;
- `PeerSyncResult`/`PeerSyncProgress`, `IPeerTransport`;
- in-memory тесты: первый обмен, инкремент в обе стороны, удаления, картинки,
  два телефона через десктоп, повторный запуск, чужой `syncId`, токен/срок,
  пагинация, неизменность облачного outbox.

Следующий этап — framed TCP/TLS, сертификат/pinning, loopback-тесты. После него —
десктопный хост и Android-клиент.

Известное ограничение core: запись на самой отметке watermark может прийти/уйти
повторно; применение идемпотентно. Записи с одинаковым `LastChange` не разрезаются
между страницами; `Watermark` хранится как max `LastChange`, а `Next` — как
следующая миллисекунда для страницы.
