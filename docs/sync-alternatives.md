# Синхронизация: варианты без S3, со сменой концепции и гибриды

> Исследование по состоянию кода на 10.11.2026. Задача — предложить способы синхронизации
> помимо S3-хранилища: (1) с минимальными изменениями текущей концепции, (2) со сменой
> концепции, (3) гибридные. Оценки трудозатрат — для одного разработчика, знакомого с
> проектом, без учёта отладки на реальных аккаунтах провайдеров.

---

## 0. Кратко

1. **Текущая концепция почти не зависит от S3.** S3 «прошит» в пяти узлах
   (конфиг, реализация хранилища, фабрика, проверка включения, UI/QR). Весь протокол —
   дельты, ревизии, снапшоты, outbox, LWW-слияние — уже транспортно-нейтрален.
2. **Ближайшие варианты без смены концепции:** локальная/сетевая папка (в том числе
   синхронизируемая Syncthing, Яндекс.Диском, OneDrive), WebDAV (Облако Mail, Nextcloud,
   Яндекс.Диск с подпиской 360), SFTP. S3-совместимые провайдеры (Яндекс Object Storage,
   VK Cloud, Selectel, R2, B2) — это вообще смена только настроек.
3. **Главная проблема — не транспорт, а протокол.** Единый `manifest.json` предполагает
   одного писателя; параллельный push с двух устройств теряет дельту, а аргумент
   `ifMatchEtag` в текущем S3-адаптере игнорируется. Поэтому «просто добавить WebDAV»
   недостаточно: нужен либо CAS (не у всех провайдеров), либо журнал по устройствам.
4. **Рекомендуемый путь:**
   - этап 0 — закрыть конкурентность, идемпотентность, checkpoint снапшота, ретеншен (2–4 дня);
   - этап 1 — обобщить конфиг и UI до «провайдеров», добавить «папку» и WebDAV (4–6 дней);
   - этап 2 — журнал по устройствам + опциональное E2E-шифрование (2,5–3,5 недели);
   - этап 3 (опционально) — Яндекс.Диск REST как «вход по кнопке» и/или PocketBase для
     синхронизации без кнопки.
5. **Смена концепции** (свой сервер, realtime, P2P) оправдана, только если нужна
   синхронизация «сама собой» или больше 3–4 устройств. Начинать с неё дорого и рискованно.

### 0.1 Карта вариантов

| Категория | Варианты | Что меняется |
|---|---|---|
| **Концепция та же** | другой S3-провайдер, папка, WebDAV, SFTP, REST облаков, Git, Telegram | только транспорт; протокол, дельты, LWW и кнопка остаются |
| **Концепция меняется** | свой sync-сервер, PocketBase/Supabase/Appwrite, CouchDB/CRDT, P2P, отказ от синхронизации | появляется сервер/новая модель слияния или исчезает обмен |
| **Гибриды** | журнал по устройствам, P2P + облако, E2E-шифрование, раздельное хранение, автосинхронизация | транспорт остаётся файловым, но меняется координация или добавляется слой |

## 1. Что считается текущей концепцией

### 1.1 Пять свойств, которые хочется сохранить

1. **Локальная LiteDB — источник истины.** Приложение работает офлайн, сеть нужна только
   на время синхронизации.
2. **Одна база = один `SyncId`.** Настройки синхронизации хранятся в конфиге конкретной
   базы, баз может быть несколько.
3. **Синхронизация ручная**, по кнопке, только для активной базы.
4. **Транспорт — плоское файловое хранилище** с иерархическими ключами: положить/прочитать
   объект, проверить существование, удалить.
5. **Обмен — дельты в журнале ревизий** плюс периодический полный снапшот базы; слияние —
   last-write-wins по `LastChange` с tombstone-записями (`DeletedAt`).

### 1.2 Где S3 действительно «прошит»

| Место | Файл | Роль |
|---|---|---|
| Модель настроек | `src/FamilyMoney/Configuration/S3StorageConfiguration.cs` | поля S3 (URL, bucket, регион, ключи) |
| Настройки базы | `src/FamilyMoney/Configuration/DatabaseConfiguration.cs:15` | свойство `S3` |
| Реализация | `src/FamilyMoney/Sync/S3SyncObjectStore.cs` | адаптер FluentStorage → `ISyncObjectStore` |
| Фабрика | `src/FamilyMoney/Sync/SyncObjectStoreFactory.cs`, `NullSyncObjectStoreFactory.cs` | выбор реализации по провайдеру |
| Проверка включения | `src/FamilyMoney/Sync/SyncService.cs:41-52` | требует `Bucket`, `AccessKey`, `SecretKey` |
| UI базы | `src/FamilyMoney/ViewModels/Settings/S3StorageViewModel.cs`, `src/FamilyMoney.Desktop/Views/DatabaseWindow.axaml:90-118` | вкладка «S3» |
| Тексты и кнопки | `src/FamilyMoney.Desktop/Views/SettingsView.axaml:329-424`, `src/FamilyMoney.Navigation/Pages/SettingsPage.axaml` | «Синхронизация S3» |
| QR-код | `src/FamilyMoney/Configuration/DatabaseQrPayload.cs` | передача настроек базы и синхронизации между устройствами |
| DI | `src/FamilyMoney/AppInit.cs:84,90` | регистрация фабрики и сервиса |

Всё остальное от S3 не зависит:

- `ISyncObjectStore` — уже абстракция на 8 методов;
- `SyncService` — сценарий pull/push/snapshot;
- `SyncPaths`, `SyncManifest`, `SyncDelta`, `SyncDeltaBuilder`, `SyncEntitySerializer`;
- outbox в LiteDB (`_SyncOutbox`, `_SyncImageOutbox`) и `ApplySyncDelta`/`ApplySyncedImagesAsync`;
- `LocalSyncState` и локальное состояние устройства.

**Вывод:** замена транспорта — это один новый класс `ISyncObjectStore`, одна фабрика,
модель конфигурации и вкладка UI. Ориентир — 300–600 строк на провайдера.

### 1.3 Что нельзя терять при смене транспорта

- офлайн-работу и локальную базу как источник истины;
- ручную синхронизацию (пользователь контролирует, когда идут данные);
- независимость от конкретного облака (сегодня S3, завтра — папка);
- совместимость уже настроенных S3-баз без переезда и без потери истории ревизий;
- одинаковое поведение на Windows и Android (насколько позволяет платформа).

## 2. Ограничения текущего протокола, которые влияют на выбор

Это важно: любой новый транспорт унаследует эти проблемы, если их не закрыть заранее.

### 2.1 Один `manifest.json` — один писатель

Сценарий потери данных:

1. Устройства A и B одновременно читают manifest с `Revision = 5`.
2. Оба формируют дельту с `Revision = 6`.
3. Оба пишут в один и тот же ключ `deltas/000006.json` — побеждает последний.
4. Оба пишут manifest с `Revision = 6`; второй перезаписывает первый.
5. Оба очищают outbox.

Изменения проигравшего устройства остаются только локально и больше не попадут в облако
(пока пользователь снова не изменит ту же сущность). Для ручной синхронизации это редкий,
но реальный сценарий: «нажали на телефоне и на ноутбуке почти одновременно».

`SyncService.PushAsync` передаёт `manifestEtag` в `UploadTextAsync`, но
`S3SyncObjectStore.UploadTextAsync` этот параметр **не использует** — условной записи нет.

### 2.2 Нет идемпотентности push

Если дельта загрузилась, а manifest — нет, outbox не очищается. Следующая синхронизация
создаст новую ревизию с теми же изменениями. LWW это в основном скрывает, но журнал растёт,
а снапшоты могут оказаться «впереди» реально применённых данных.

### 2.3 Снапшот копируется без checkpoint

Бэкап делает `db.Checkpoint()` перед `File.Copy` (`LiteDbRepository.cs:278-283`), а
`SyncService` загружает файл базы как есть (`UploadFileAsync(snapshotKey, databasePath)`).
Если LiteDB держит часть данных в лог-файле, снапшот может быть неполным. Нужен тот же
checkpoint (или временная копия через существующий механизм бэкапа).

### 2.4 Ошибка загрузки картинки не откатывает ревизию

`PullAsync` применяет дельту, затем пытается скачать картинки; если скачивание не удалось,
ревизия всё равно считается применённой. Картинка больше не будет запрошена, пока не придёт
новая дельта по этой сущности.

### 2.5 Нет ретеншена

Снапшот пишется каждые 50 ревизий, дельты не удаляются, старые снапшоты тоже. База с
картинками может весить десятки мегабайт — это регулярная полная выгрузка. Нужна политика:
хранить последний снапшот + дельты после него, остальное чистить.

### 2.6 Секреты лежат открыто

`AccessKey`/`SecretKey` хранятся в JSON настроек. Исторически они попадали и в QR-код;
теперь QR по умолчанию содержит только несекретные параметры. Передача ключей осталась
отдельной явной галочкой для настройки телефона. Для новых провайдеров это тем важнее,
чем шире область доступа (весь Диск вместо папки приложения).

### 2.7 LWW и часы устройств

Слияние по `DateTime.UtcNow` означает, что сбитые часы или ручная правка времени могут
«победить» более новую правку. В семейном приложении это терпимо, но для диагностики
конфликтов полезно гибридное логическое время (HLC) и журнал конфликтов.

### 2.8 Автосинхронизации нет

Исторически синхронизация на старте была (`git show 7920d1c`), затем удалена. Вероятная
причина: она выполнялась параллельно с инициализацией UI и могла менять базу под ногами.
Если делать автоматизацию, то после загрузки, в фоне, с отменой и уведомлением.

**Вывод:** до расширения списка провайдеров стоит закрыть п. 2.1–2.5. Иначе каждый новый
транспорт будет получать те же ошибки, а поддержка будет расти быстрее, чем польза.

## 3. Критерии выбора

| Критерий | Что важно для FamilyMoney |
|---|---|
| Инфраструктура | нужен ли сервер/VPS или достаточно аккаунта в облаке |
| Доступность в РФ | регистрация, оплата, стабильность |
| Авторизация | насколько просто подключить второе устройство (QR, логин, ключи) |
| Мобильность | работает ли на Android, нет ли фоновых ограничений |
| Офлайн | можно ли работать без сети (у всех вариантов — да, вопрос в транспорте) |
| Конкурентная запись | есть ли CAS/условная запись или нужен журнал по устройствам |
| Объём и трафик | полные снапшоты, картинки, мобильный интернет |
| Трудозатраты | дни/недели на адаптер + UI + тесты |
| Эксплуатация | обновления, TLS, бэкапы, мониторинг |
| Приватность | кто видит финансовые данные и фото |
| Долгосрочность | не закроется ли API/сервис через год |

## 4. Группа A — другой транспорт, концепция та же

Все варианты ниже реализуются как ещё одна реализация `ISyncObjectStore`; `SyncService`,
формат дельт и слияние не меняются.

### A0. Другой S3-совместимый провайдер

Формально это «не другой способ», а другой поставщик, но именно он решает 80 % проблем
пользователей S3: доступность, оплата, регион, привычный кабинет.

| Провайдер | Комментарий |
|---|---|
| Яндекс Object Storage | S3 API, российская оплата, есть бесплатный грант |
| VK Cloud Object Storage | S3 API, российская оплата |
| Selectel / Cloud.ru / MTS | S3 API, российские ЦОДы |
| Cloudflare R2 | S3 API, нет egress-платы, но оплата и доступность из РФ — проверить |
| Backblaze B2 / Wasabi | S3 API, дешёвое хранение |
| Своё S3 на NAS/сервере (Garage, SeaweedFS, Ceph; community-MinIO архивирован) | полный контроль, нужен свой сервер |
| Storj / IDrive e2 | S3-шлюз, нишевые |

**Что сделать:** пресеты endpoint/региона в UI и подсказки «где взять ключи».
**Трудозатраты:** 0,5–1 день. **Риски:** у разных S3-совместимых реализаций отличается
поддержка `If-Match`, path-style и листинга; это надо проверять, а не предполагать.

**Вердикт:** самый дешёвый шаг, но концепцию не меняет. Держать как поддерживаемый вариант.

### A1. Папка: локальная, сетевая или синхронизируемая сторонним клиентом

**Идея.** `FolderSyncObjectStore` пишет те же ключи в каталог на диске. Каталог может быть:
- локальным (USB-флешка, второй диск);
- сетевым (SMB/UNC на NAS);
- папкой, которую синхронизирует сторонний клиент: Syncthing, Resilio, Яндекс.Диск,
  OneDrive, Dropbox, Nextcloud Desktop.

**Реализация.** `Directory`/`File`, атомарная запись через временный файл и `File.Move`,
ETag = время изменения + размер, листинг через `Directory.EnumerateFiles`. Ориентир —
150–250 строк + тесты.

**Важно:** синхронизировать нужно **только каталог обмена** (`familymoney/{syncId}/...`),
а не живой файл `database.db`. LiteDB нельзя класть в облачную папку: частичная копия,
конфликтные копии и блокировки файла приведут к повреждению. Это же правило — для любых
«папочных» схем.

**Плюсы:** нет аккаунтов и ключей; бесплатно; работает на любом NAS; легко объяснить.
**Минусы:** на Windows и Android нужен доступ к одной и той же папке; на Android — SAF
(`DocumentFile`) или папка приложения, которую умеет синхронизировать клиент; облачные
клиенты могут держать «файлы по требованию» и отдавать пустышки; конфликтные копии
(`file (1).json`) нужно обнаруживать и не считать данными.

**Трудозатраты:** 2–4 дня (desktop), +2–3 дня на Android SAF.
**Вердикт:** лучший бесплатный вариант для «два ПК и NAS»; хороший первый провайдер после
рефакторинга.

### A1-бис. Обмен целыми копиями базы (самый грубый вариант)

Если дельты кажутся сложными, можно синхронизировать не изменения, а **полные копии**:
каждое устройство кладёт в общую папку `snapshots/{deviceId}-{timestamp}.db` с sidecar-JSON
(`syncId`, устройство, ревизия, время, контрольная сумма). Перед работой устройство смотрит
самую новую копию и, если она новее локальной, восстанавливает её (с предварительным
бэкапом). Если локальные изменения не отправлены, а удалённая копия новее — создаётся
конфликтная копия и пользователь выбирает, что оставить.

**Плюсы:** не нужен протокол дельт; работает с любой папкой; переиспользует существующие
бэкап/восстановление; понятно пользователю.
**Минусы:** полный трафик каждый раз; слияние на уровне всей базы (LWW всей копией), а не
сущностей; риск потерять изменения; нет истории; конфликты решаются вручную.
**Трудозатраты:** 3–5 дней. **Вердикт:** аварийный/самый простой режим, не основной.

### A2. WebDAV

**Идея.** Тот же файловый протокол, но по HTTP: `PROPFIND` (метаданные и листинг), `GET`,
`PUT`, `DELETE`, `MKCOL`. Авторизация — Basic с паролем приложения поверх TLS.

**Провайдеры:**

| Провайдер | Доступность | Нюанс |
|---|---|---|
| Облако Mail.ru | доступен без отдельной подписки (проверить лимиты) | пароль приложения |
| Nextcloud / ownCloud | свой сервер или хостинг | лучший «свой облак» без S3 |
| Яндекс.Диск | с 22.06.2026 требует подписку Яндекс 360 | WebDAV-пароль создаётся отдельно |
| VK WorkSpace | корпоративный | проверить тариф |
| Box / HiDrive / NAS (Synology, TrueNAS) | по ситуации | у каждого свои лимиты |
| rclone serve webdav | где угодно | удобно для тестов |

**Реализация.** `HttpClient` + разбор `PROPFIND` (XML), ~300–400 строк; альтернатива —
пакет `WebDav.Client`. ETag у большинства серверов есть, `If-Match` поддерживается не
везде — это надо проверять и не полагаться на него.

**Плюсы:** одно облако на все устройства; не нужен S3 и его ключи; работает на Android
через обычный `HttpClient`; у Mail.ru — без отдельной подписки, у Nextcloud — свой сервер.
**Минусы:** пароли приложений и 2FA; лимиты и троттлинг; у Яндекс.Диска доступ стал
платным; слабая поддержка условной записи; XML-квирки серверов.

**Трудозатраты:** 3–5 дней. **Вердикт:** лучший «облачный» вариант без S3 для РФ на
сегодня; делать вместе с A1.

### A3. SFTP/FTP

**Идея.** Хранилище на VPS/NAS: SFTP по SSH или FTP/FTPS. У FluentStorage есть отдельные пакеты
`FluentStorage.SFTP` (SSH.NET) и `FluentStorage.FTP` (FluentFTP) — их можно подключить
вместо собственного клиента.

**Плюсы:** полный контроль, знакомо техническим пользователям, работает на Android.
**Минусы:** нужен сервер и его обслуживание; порт 22 могут блокировать мобильные операторы;
FTP без TLS небезопасен; CAS нет, только перезапись и переименование.
**Трудозатраты:** 2–3 дня. **Вердикт:** ниша для тех, у кого уже есть VPS/NAS.

### A4. Нативные REST API облаков

Это уже не «файловое хранилище», а API с OAuth; но для `ISyncObjectStore` разница
невелика — нужно лишь реализовать загрузку/скачивание/листинг.

| Провайдер | Модель доступа | Маркер версии | OAuth | Трудозатраты | РФ |
|---|---|---|---|---|---|
| Яндекс.Диск | папка приложения (`app:/`, scope `cloud_api:disk.app_folder`) | `md5`, `modified` | loopback/custom scheme | 5–8 дней | хорошо |
| Dropbox | App Folder | `rev`, `content_hash` | PKCE | 5–7 дней | доступность проверить |
| Google Drive | `appDataFolder` | `etag`, `changes` | loopback/custom scheme | 6–9 дней | ограничения |
| OneDrive | `special/approot` | `eTag`, `delta` | MSAL | 6–9 дней | проверить |

**Яндекс.Диск** выглядит лучшим «входом по кнопке» для РФ: пользователь авторизуется,
приложение получает доступ только к своей папке, второе устройство авторизуется так же и
видит те же файлы. Не нужно передавать секреты через QR. Но это отдельный OAuth-клиент,
хранение токена, обработка истечения и отзыв доступа.

**Google Drive / Dropbox / OneDrive** дают хороший международный охват, но каждое —
отдельная интеграция, проверка приложения и поддержка. Делать все сразу не стоит.

**Вердикт:** Яндекс.Диск — опциональный этап 3; остальные — только при реальном спросе.

### A5. Экзотические транспорты

| Транспорт | Как | Ограничения | Трудозатраты | Вердикт |
|---|---|---|---|---|
| Git-репозиторий | дельты как файлы с уникальными именами, push/pull | Android-клиент тяжёлый; рост репозитория; PAT/SSH | 3–5 дней | ниша для гика |
| Telegram-бот/канал | отправка JSON-дельты документом, `message_id` как ревизия | Bot API: скачивание до 20 МБ, отправка документа до 50 МБ; нет CAS; фото сжимаются; нужен E2E | 3–5 дней | демо, не основной |
| E-mail/IMAP | дельта во вложении | медленно, лимиты, спам-фильтры | 3–5 дней | нет |
| IPFS/Arweave | контент-адресуемое хранилище | нужен пиннинг/шлюз, без шифрования данные публичны | 5–7 дней | нет |
| USB/QR/share | экспорт пакета, импорт на другом устройстве | QR вмещает килобайты, не мегабайты | 1–2 дня | аварийный fallback |

**Про Telegram отдельно:** соблазн «бесплатное облако без регистрации» велик, но это
нарушает стабильность (лимиты, блокировки), а картинки чеков через `sendPhoto` теряют
качество. Как основной транспорт — нет; как эксперимент с E2E — возможно.

## 5. Группа B — смена концепции

### B1. Собственный sync-сервер

**Идея.** Приложение перестаёт быть «файлы в чужом облаке» и получает свой backend:
он принимает дельты, атомарно назначает глобальную ревизию, хранит снапшоты и картинки,
отдаёт изменения другим устройствам (в идеале — в реальном времени через WebSocket/SSE).

```
Desktop ─┐                         ┌─ SQLite/Postgres
         ├── HTTPS (device token) ─┤  deltas, devices, snapshots, images
Android ─┘                         └─ SignalR/SSE → push другим устройствам
```

**Что нужно:** ASP.NET Core minimal API, схема БД, авторизация устройств (invite-код →
токен), идемпотентный push, пагинация pull, отдача картинок, миграции, TLS, бэкапы,
мониторинг. На клиенте — новый интерфейс `ISyncApiClient` (или `ISyncObjectStore`,
маппящий ключи на API, но это менее честно).

**Плюсы:** корректная конкурентность, настоящая синхронизация «без кнопки», аудит,
несколько пользователей, потенциально веб-версия и общий доступ.
**Минусы:** хостинг, TLS, бэкапы, обновления, безопасность, доступность 24/7; это уже
продукт-сервис, а не приложение; 3–5 недель + постоянная эксплуатация.

**Когда оправдано:** если цель — «поставил и забыл», больше 3–4 устройств, удалённые
родственники, общий семейный бюджет с ролями.

### B2. Готовый BaaS

| Платформа | Что даёт | Плюсы | Минусы | Трудозатраты |
|---|---|---|---|---|
| **PocketBase** | один бинарник, SQLite, REST, realtime (SSE), auth, файлы, админка, бэкапы | проще всего поднять на VPS/NAS/Raspberry Pi; нет vendor lock; реальный realtime | нужно своё железо/хостинг; коллекции и правила доступа настраиваются вручную | 2–3 недели с клиентом |
| Supabase | Postgres, RLS, Realtime, Storage, Auth | зрелость, SQL, бесплатный тариф | доступность/оплата из РФ, vendor lock, больше DevOps | 2–3 недели |
| Appwrite | self-hosted, realtime, storage | самодостаточный | тяжёлый Docker-стек, больше ресурсов | 2–3 недели |
| Firebase | Firestore + offline | хороший offline на Android | .NET desktop без полноценного offline; доступность в РФ | — |

**PocketBase — лучший компромисс «смена концепции без большого DevOps».** Схема:
`sync_deltas` (sync_id, device_id, seq, payload, created), `sync_images` (sync_id, entity_id,
file), `sync_devices`; уникальный индекс `(sync_id, device_id, seq)` заменяет CAS; realtime-
подписка на `sync_deltas` даёт мгновенный pull. Клиент — тот же формат дельт, но транспорт
REST + SSE.

**Важно:** это всё равно «свой сервер» — просто чужой и проверенный. Появляются хостинг,
обновления и ответственность за данные.

### B3. CouchDB-репликация, CRDT и sync-движки

| Вариант | Почему не подходит |
|---|---|
| CouchDB/PouchDB-репликация | пришлось бы заменить LiteDB или держать её как кэш; конфликты всё равно разрешать; .NET-клиенты слабые; большой рефакторинг |
| CRDT (Automerge, Yjs) | нет зрелого .NET/Android-стека; для финансовых записей LWW по полям достаточно; цена внедрения не оправдана |
| PowerSync / ElectricSQL | Postgres↔SQLite, ориентированы на JS/Flutter; LiteDB не поддерживают |

**Что действительно стоит улучшить вместо CRDT:** гибридное логическое время (HLC),
разрешение конфликтов по полям и журнал конфликтов для пользователя. Это дешевле и
понятнее, чем CRDT.

### B4. P2P в локальной сети

**Идея.** Дома телефон и ноутбук синхронизируются напрямую по Wi-Fi, без облака:
одно устройство поднимает HTTP-сервер, второе находит его через mDNS/UDP-broadcast,
пара проверяется QR-кодом (отпечаток сертификата + одноразовый код), дельты передаются
напрямую.

**Плюсы:** бесплатно, быстро, приватно, работает без интернета.
**Минусы:** оба приложения должны быть открыты; нужен один Wi-Fi без client isolation;
Android душит фоновые сервисы; гостевые сети; сложность TLS/обнаружения; 3–5 недель.

**Вердикт:** красивый гибрид «дома — напрямую, вне дома — облако», но не первый шаг.
Начинать с прототипа на сокетах, а не с встроенного Kestrel на Android.
Детальный проект: [sync-p2p-wifi.md](sync-p2p-wifi.md).

### B5. Отказ от синхронизации

**Идея.** Одна база на одном устройстве, резервные копии и ручной перенос файла.
Уже почти поддерживается: бэкап/восстановление есть.

**Плюсы:** ноль инфраструктуры и кода, никаких конфликтов.
**Минусы:** теряется ключевая возможность «телефон + ноутбук».
**Вердикт:** честный fallback для тех, кому синхронизация не нужна; не развивать.

## 6. Гибриды

### G1. Журнал по устройствам (multi-writer) — главный гибрид

**Проблема, которую решает:** убрать единый `manifest.json` и необходимость CAS, сохранив
файловый транспорт, дельты и LWW.

**Схема хранения:**

```
familymoney/{syncId}/
  devices/{deviceId}/manifest.json      # последняя seq этого устройства
  devices/{deviceId}/deltas/{seq}.json  # дельты только этого устройства
  snapshots/base-{rev}.db               # неизменяемый базовый снапшот
  images/{entityId}                     # как сейчас
```

**Алгоритм:**

1. Каждое устройство пишет **только в свой префикс**, поэтому одновременная запись с двух
   устройств не конфликтует.
2. При pull устройство листает `devices/*/manifest.json`, сравнивает с локальной картой
   `applied[deviceId]` и дочитывает недостающие дельты. Порядок между устройствами не важен:
   слияние всё равно по `LastChange`.
3. При push устройство увеличивает свою `seq` и пишет дельту, затем свой manifest.
4. Новое устройство: скачивает базовый снапшот (он содержит карту `applied` на момент
   создания) и дочитывает дельты, которых нет в карте.
5. Старые дельты и снапшоты чистятся по политике: последний снапшот + дельты после него.

**Что меняется в коде:** `SyncPaths` (ключи с `deviceId`), `LocalSyncState` (карта
`applied` по устройствам), `SyncService.PullAsync/PushAsync`, логика снапшота, миграция
старого формата. `ISyncObjectStore` нужно дополнить листингом.

**Оговорки.** Картинки остаются общими (`images/{entityId}`): при одновременной замене
фото одной сущности с двух устройств сработает LWW по метаданным, как и сейчас. Внутри
одного устройства дельты упорядочены по `seq`; между устройствами глобального порядка нет
и не нужно — слияние идёт по `LastChange`.

**Плюсы:** работает с любым «глупым» хранилищем (папка, WebDAV, Яндекс.Диск, Telegram);
нет потери дельт при параллельном push; проще отладка (у каждого устройства свой журнал).
**Минусы:** больше объектов и листингов; нужен ретеншен; старые клиенты несовместимы —
нужен version-gate и предупреждение «обновите приложение на всех устройствах».
**Трудозатраты:** 1,5–2,5 недели с миграцией и тестами.

**Вердикт:** ключевое улучшение, если планируется больше одного облака и больше двух
устройств. Именно оно делает WebDAV/папку по-настоящему безопасными.

### G2. P2P дома + облако вне дома

Один и тот же формат дельт, два транспорта: при старте синхронизации сначала пробуем
найти пира в локальной сети (быстро, бесплатно), если не нашли — идём в облако. Требует
G1 (или CAS), иначе конфликты. Трудозатраты: 3–5 недель. Отличный UX для семьи, но
дорого как первый шаг.

### G3. Раздельное хранение: журнал отдельно, файлы отдельно

Метаданные и дельты — в лёгком хранилище (папка/WebDAV/PocketBase), картинки и снапшоты —
в S3/объектном хранилище. Полезно, если у провайдера маленькие лимиты на объект (Telegram)
или дорогой egress. Минусы: две конфигурации, два набора ошибок, частичные отказы.
**Вердикт:** только при явном ограничении, не как общая архитектура.

### G4. E2E-шифрование поверх любого транспорта

Облако видит имена объектов и размеры, но не содержимое. Схема:

- ключ базы выводится из парольной фразы через Argon2id + соль (хранится в конфиге);
- каждая дельта и каждая картинка шифруются AES-GCM;
- ключ передаётся на второе устройство через QR (это **не** пароль от облака) или вводится
  вручную;
- имена объектов можно оставить как есть (утечка метаданных: количество и время ревизий),
  либо заменить на HMAC-идентификаторы.

**Плюсы:** можно безопасно использовать Облако Mail, Яндекс.Диск, Dropbox, Telegram;
финансовые данные и фото чеков не читаются провайдером.
**Минусы:** потеря ключа = потеря данных; нужен recovery-код; UI ввода пароля; шифрование
чуть усложняет отладку.
**Трудозатраты:** 4–6 дней. **Вердикт:** настоятельно рекомендуется для любых
потребительских облаков.

### G5. «Координатор» + S3

Крошечный сервис (или Durable Object) только для атомарной выдачи ревизии/блокировки,
данные — в S3. Решает CAS, но добавляет зависимость от сервера ради одной операции.
По сравнению с G1 — хуже: и сервер нужен, и S3 остаётся. **Не рекомендуется.**

### G6. Автосинхронизация как UX-слой

Это не транспорт, но без неё «удобство» не меняется:

- триггеры: старт приложения (после загрузки UI), закрытие, смена сети, таймер;
- дебаунс и отмена, если пользователь начал операцию;
- Android: WorkManager с минимальным интервалом 15 минут, только при сети и зарядке;
- уведомление о результате и о конфликтах;
- не блокировать UI и не пересоздавать базу во время правки.

**Трудозатраты:** 3–5 дней. **Вердикт:** делать после этапа 1, когда транспорт стабилен.

## 8. Рекомендация и дорожная карта

### Принципы

1. **Транспорт — деталь.** Не превращать приложение в коллекцию из десяти облачных SDK.
   Два-три провайдера, покрывающих сценарии, лучше десяти недоделанных.
2. **Сначала безопасность протокола, потом новые провайдеры.** Иначе баги размножаются.
3. **Ручная синхронизация — норма.** Автосинхронизация — отдельный UX-слой, а не замена.
4. **Шифрование — до публичных облаков.** Особенно если в QR/конфиге будут токены.

### Этап 0. Целостность текущей синхронизации (2–4 дня) — сделано

- [x] Условная запись manifest: `If-Match`/`If-None-Match` через AWS SDK, с откатом на
      безусловную запись и проверкой manifest после неё.
- [x] Распределённая блокировка `sync.lock` с TTL; повторный вход с того же устройства.
      В протоколе 3 (этап 2) блокировка не нужна: каждое устройство пишет свой журнал.
- [x] Проверка manifest после записи и повтор при конфликте (до трёх попыток).
- [x] `Checkpoint` перед загрузкой снапшота (как в бэкапе).
- [x] Повтор картинок: неудачная загрузка не двигает `AppliedRevision`; push не публикует
      дельту, если локальная картинка не найдена.
- [x] Идемпотентность push: `OperationId` + хэш отправленных изменений; outbox очищается
      только для вошедших в дельту записей.
- [x] Ретеншен снапшотов: после успешной публикации нового снапшота старый удаляется.
      Дельты пока не удаляются — это можно делать только зная, что все устройства ушли вперёд.
- [x] Тесты: фейковый `ISyncObjectStore`, конфликт manifest, повтор после сбоя очистки
      outbox, отказ загрузки картинки, блокировка, отсутствие условной записи.

**Что осталось за рамками этапа 0:**

- общий журнал всё ещё использует ключ `deltas/{revision}.json`; при синхронизации
  старой версией приложения (без блокировки) возможна гонка — нужен version-gate или G1;
- TTL блокировки опирается на часы устройства;
- удаление старых дельт требует учёта последней ревизии каждого устройства (G1);
- смешанные версии приложения: новый клиент видит старый manifest, но старый клиент
  не знает о блокировке и `OperationId`.

### Этап 1. Провайдеры без смены протокола (4–6 дней) — сделано

- [x] `SyncStorageConfiguration` с `Provider` и вложенными настройками; миграция старых
      настроек `S3` без потери данных. Старое поле `S3` продолжает зеркалироваться при
      сохранении, чтобы не ломать прежние версии приложения.
- [x] `FolderSyncObjectStore` для локального, сетевого и синхронизируемого каталога.
      SAF-адаптер для Android не делался: на телефоне каталог должен быть доступен
      приложению как обычный путь.
- [x] `WebDavSyncObjectStore` + пресеты Mail.ru, Яндекс.Диска, Nextcloud; Basic-авторизация,
      MKCOL для вложенных папок, условная запись.
- [x] UI: вкладка «Синхронизация» с выбором провайдера и динамическими полями, пресеты
      S3/WebDAV, выбор папки, кнопка «Проверить подключение» (пробная запись и удаление).
- [x] QR v2: по умолчанию только провайдер и несекретные параметры; ключи S3 и пароль
      WebDAV не попадают. Для настройки телефона, где нет формы ввода ключей, есть явная
      галочка «Передавать ключи и пароли» с предупреждением. Старые QR v1 читаются.
- [x] Тесты: Folder и WebDAV на HTTP-заглушке, миграция конфига, QR без секретов,
      проверка подключения, выбор фабрики.

**Результат:** S3 остаётся, но появляются бесплатные и «облачные без S3» варианты; уже
закрывает большинство семейных сценариев.

### Этап 2. Журнал по устройствам и шифрование (2,5–3,5 недели) — сделано

- [x] G1: ключи `devices/{deviceId}/manifest.json` и
      `devices/{deviceId}/deltas/{seq}.json`; карта `AppliedByDevice` в `LocalSyncState`.
- [x] Листинг объектов в `ISyncObjectStore`: S3, папка, WebDAV (PROPFIND), Null.
- [x] Старый общий журнал: при первом запуске дочитывается до актуальной ревизии,
      затем помечается `LegacyMigrated`; snapshot фиксирует перенесённые данные.
- [x] Базовые снапшоты: уникальный ключ, sidecar с `AppliedByDevice`, хранение двух
      последних, восстановление на новом устройстве и дочитывание хвостов журналов.
      Дельты пока не удаляются: устройство, отставшее от снапшота, но имеющее локальные
      правки, должно дочитать их, а не восстанавливать снапшот поверх себя.
- [x] G4: AES-GCM для текстов, картинок, снапшотов; PBKDF2-SHA256, соль, key-check.
      Ключ хранится на устройстве, парольная фраза — нет. Есть код восстановления.
- [x] UI шифрования: включение, парольная фраза, проверка ключа, код восстановления;
      отключить шифрование после включения нельзя без пересоздания хранилища.
- [x] QR: соль и key-check передаются как несекретные параметры; ключ попадает только
      при явной галочке «Передавать ключи и пароли».
- [x] Тесты: три устройства, параллельный push, новый девайс из снапшота, миграция
      старого журнала, отказ по неверному ключу, WebDAV-листинг, recovery-код.

**Ограничения:** старые клиенты (протокол 2) не знают о журналах устройств; после
перехода их нужно обновить. Смена парольной фразы и отключение шифрования не
поддерживаются — это потребовало бы перезаписи всего хранилища. Потеря и пароля,
и кода восстановления означает потерю данных.

### Этап 3. Опциональные ветки (по спросу)

- [ ] **Яндекс.Диск REST** — «войти и синхронизировать» для РФ (1–1,5 недели).
- [ ] **PocketBase** — синхронизация без кнопки, realtime (2–3 недели + хостинг).
- [ ] **P2P LAN** — дома без облака (3–5 недель, прототип раньше).
      [Детальный проект P2P по Wi-Fi](sync-p2p-wifi.md) готов.
      Core-прототип этапа 1 (state-based обмен и тесты) реализован; сеть и UI — следующие.
      План дополнен режимом «десктоп — облачный публикатор» для P2P-изменений.
- [ ] Dropbox/Google/OneDrive — только если появится запрос.

### Чего не делать сейчас

- Собственный сервер «с нуля» — дорого в эксплуатации и не решает текущую боль.
- CouchDB/CRDT — несовместимо с LiteDB и не даёт выигрыша для LWW-записей.
- Telegram как основной транспорт — нестабильно и небезопасно без E2E.
- Десять облачных SDK одновременно — поддержка съест все выгоды.

## 9. План изменений в коде

### 9.1 Конфигурация

```csharp
public enum SyncProvider
{
    None = 0,
    S3 = 1,
    WebDav = 2,
    Folder = 3,
    // YandexDisk = 4, ...
}

public sealed class SyncStorageConfiguration
{
    public SyncProvider Provider { get; set; } = SyncProvider.None;
    public bool Enabled { get; set; }
    public S3StorageConfiguration S3 { get; set; } = new();
    public WebDavStorageConfiguration WebDav { get; set; } = new();
    public FolderStorageConfiguration Folder { get; set; } = new();
}
```

Совместимость: оставить `DatabaseConfiguration.S3` и при загрузке конфига мигрировать
`S3.Enabled == true` → `Sync.Provider = S3`. Старые версии приложения продолжат видеть
`S3`, новые — `Sync`; на переходный период можно писать оба блока.

### 9.2 Интерфейс хранилища

Добавить листинг и возможности:

```csharp
public sealed record SyncObjectInfo(
    string Key, long Size, string? ETag, DateTimeOffset? ModifiedAt);

public sealed record SyncStoreCapabilities(
    bool SupportsList,
    bool SupportsConditionalWrite,
    bool SupportsDelete,
    long? MaxObjectSize);

    // существующие методы...

        string prefix, CancellationToken cancellationToken = default);
    SyncStoreCapabilities Capabilities { get; }
}
```

`SyncService` использует `Capabilities`: если условной записи нет, включает режим G1 или
предупреждает пользователя.

### 9.3 Фабрика и сервис

- `ISyncObjectStoreFactory.Create(SyncStorageConfiguration)` — выбор по `Provider`.
- `SyncService.IsEnabled` → `factory.Validate(config)` (у каждого провайдера свои
  обязательные поля; для папки — существующий каталог, для WebDAV — URL и логин).
- Тексты `SyncResult` — без «S3»; сообщение об ошибке включает провайдера и шаг.
- Добавить `LastSyncAt`/`LastSyncResult` в локальное состояние (для UI).

### 9.6 QR и безопасность

`DatabaseQrPayload` v2:

```json
{
  "app": "familymoney",
  "version": 2,
  "syncId": "...",
  "name": "Семейный бюджет",
  "path": "database.db",
  "backupsFolder": "Backups",
  "maxBackups": 10,
  "sync": { "provider": "webdav", "url": "https://...", "login": "..." }
}
```

- По умолчанию никаких `SecretKey`/паролей в QR: только провайдер, endpoint/bucket,
  логин WebDAV и путь к папке. Для настройки телефона есть явная галочка «Передавать
  ключи и пароли» с предупреждением; старый QR v1 продолжает читаться.
- Для папки/локальной сети — одноразовый pairing-код с TTL.
- При E2E — отдельный ключ базы, не равный паролю облака.

### 9.7 Тесты

- In-memory `ISyncObjectStore` с эмуляцией задержек и сбоев.
- Два устройства: A меняет счёт, B — транзакцию; оба синхронизируются; проверка слияния.
- Параллельный push: A и B одновременно; проверка, что обе дельты применились (G1) или
  что конфликт обнаружен (CAS).
- Обрыв после загрузки дельты, но до manifest; повторная синхронизация.
- Новое устройство: снапшот + дельты; проверка полноты.
- Миграция конфига S3 → Sync без потери полей.
- WebDAV: тест на локальном сервере (или заглушке `HttpListener`).
- Шифрование: round-trip, неверный ключ, смена ключа.

## 10. Риски

| Риск | Проявление | Смягчение |
|---|---|---|
| Потеря дельты при параллельном push | изменения не доходят до других | G1 или CAS + тест |
| Сбитые часы | «старая» правка побеждает | HLC, предупреждение, журнал конфликтов |
| Снапшот без checkpoint | потеря последних записей | checkpoint/бэкап-копия |
| Рост хранилища | полные снапшоты каждые 50 ревизий | ретеншен, снапшот по требованию |
| Секреты в конфиге/QR | утечка доступа | не хранить в QR, DPAPI/Keystore, E2E |
| Провайдер закрыл доступ | синхронизация перестала работать | абстракция + 2–3 провайдера, экспорт |
| Лимиты и троттлинг | ошибки 429/413 | ретраи с backoff, разбиение файлов |
| Android-фон | синхронизация не идёт | ручной режим, WorkManager, уведомления |
| OAuth-редирект | неудобно на desktop/Android | loopback + custom scheme, device flow где есть |
| Поддержка | каждый провайдер = свои баги | не больше 2–3 активных, остальные «experimental» |
| Совместимость версий | старый клиент ломает G1 | version-gate, миграция, предупреждение |

## 11. Приложение: семантика хранилищ

| Хранилище | Листинг | Условная запись | Переименование | Лимит объекта | Замечание |
|---|---|---|---|---|---|
| AWS S3 | да | `If-Match`/`If-None-Match` (SigV4) | нет (copy+delete) | 5 ТБ | у S3-совместимых поддержка различается |
| Azure Blob | да | `If-Match` по ETag | нет | очень большой | нативный ETag |
| WebDAV | `PROPFIND` | `If-Match` не везде | `MOVE` | зависит от сервера | XML-квирки |
| Папка | да | атомарный `Move` | да | ФС | не синхронизировать живой `.db` |
| Яндекс.Диск REST | да | нет (перезапись) | да (ресурсы) | по тарифу | `app:/`, OAuth |
| Dropbox | да (cursor) | `rev` в update | да | 150 МБ/запрос, сессии — больше | App Folder |
| Google Drive | да | `If-Match` по etag | да | 5 ТБ | `appDataFolder` |
| OneDrive/Graph | да (`delta`) | `If-Match` | да | 250 ГБ | `approot` |
| SFTP | да | нет | `rename` | ФС | host key |
| PocketBase | да (фильтры) | уникальный индекс | нет | настраивается | SQLite, SSE |
